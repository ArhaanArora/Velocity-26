## 1. Product vision

CyberLab is an interactive cybersecurity learning laboratory for college computer science students.

Students interact with a fictional network, observe simulated traffic, adjust infrastructure, introduce overload conditions, and investigate how defensive mechanisms affect legitimate-user availability.

The core learning experience is:

**Experiment → Observe → Investigate → Understand.**

CyberLab is NOT a real cybersecurity attack tool. Everything is an abstract browser-based educational simulation.

The application must feel like real cybersecurity monitoring software rather than a generic college learning dashboard.

## 3. Mandatory integration contract

The backend developer is implementing:

`src/engine/index.ts`

It will export:

- `simulationEngine`
- `createInitialState`
- `stepSimulation`
- `normalTrafficPreset`
- `trafficSurgePreset`
- `midnightOutagePreset`

The shared contract is located at:

`src/shared/simulationTypes.ts`

Its exact interfaces are:

```typescript
export type AttackType = "none" | "volume" | "syn";

export type SystemStatus =
  | "normal"
  | "degraded"
  | "down";

export interface SimulationConfig {
  legitRate: number;
  attackType: AttackType;
  attackRate: number;
  filterStrength: number;
  loadBalancer: boolean;
  serverCount: number;
  perServerCapacity: number;
  perServerBandwidth: number;
  perServerConnections: number;
  perServerQueue: number;
}

export interface SimulationMetrics {
  incoming: number;
  blocked: number;
  legitServed: number;
  attackServed: number;
  legitDropped: number;
  attackDropped: number;
  queueDepth: number;
  cpuPercent: number;
  bandwidthPercent: number;
  connectionPercent: number;
  queuePercent: number;
  latencyMs: number;
  legitAvailabilityPercent: number;
  status: SystemStatus;
}

export interface SimulationSnapshot
  extends SimulationMetrics {
  tick: number;
}

export interface SimulationState {
  tick: number;
  queueLegit: number;
  queueAttack: number;
  halfOpen: number;
  metrics: SimulationMetrics;
  history: SimulationSnapshot[];
}

export interface SimulationEngine {
  createInitialState(
    config: SimulationConfig
  ): SimulationState;

  stepSimulation(
    config: SimulationConfig,
    state: SimulationState
  ): SimulationState;
}
```

**Never modify this contract or rename its properties.**

If the actual shared file differs, report the mismatch and follow the actual checked-in shared contract, rather than creating an incompatible duplicate.

## 8. Simulation controls

Implement:

**Run:** advance the simulation automatically.

**Pause:** freeze simulation ticks.

**Step:** advance exactly one tick while paused.

**Reset:** restore the current mode's initial configuration and state.

Use approximately one real second per simulated tick.

Use one shared `useSimulation` hook to manage timing, state, and configuration.

Never create independent timers inside charts or visual components.

Slider changes while paused should update configuration without advancing simulation time.

Changing configuration while running should affect future ticks.

Use the engine's returned state rather than inventing intermediate server data.

## 12. Challenge Mode

Add an always-visible Challenges tab.

Implement ONE scenario:

**The Midnight Outage**

A fictional online service is experiencing severe performance problems.

When entering Challenge Mode:

1. Show an incident briefing.
2. Explain that legitimate users are experiencing failures.
3. Do not reveal the cause immediately.
4. Load the predefined challenge configuration.
5. Start the simulation.
6. Let the student investigate resource metrics.
7. Allow defensive configuration changes.
8. Track service stabilization.

Use the same dashboard and engine as Sandbox.

Do not implement a second independent simulator.

The challenge should be considered successful when legitimate availability remains at or above 85% for 15 consecutive simulated ticks.

Only count ticks while the simulation advances.

The chosen threshold is an educational challenge target, not a real-world security guarantee.

If the legitimate-user availability drops below the threshold, restart the consecutive stable-tick counter.

If the engine indicates an unhealthy state despite availability being high, show a warning and avoid presenting the service as fully healthy.

Show progress toward the stabilization target.

### Session switching

Preserve Sandbox and Challenge configurations and simulation states independently in React state.

Switching tabs should pause the inactive mode without deleting its progress.

Avoid running both modes' timers simultaneously.
